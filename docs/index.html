SECTION 1

Installation

1-1.conn requires tmux (holds the shells) and lsof (reads the process list). macOS ships lsof; install tmux with brew install tmux. On Linux, install both from the package manager.

$curl -fsSL https://conn.w0zro.com/install.sh | sh

1-2.The script downloads the release for this machine, verifies it against checksums.txt, and installs the binary to ~/.local/bin and the manpage under ~/.local/share/man. man conn is the full reference. Three variables override the script:

Table 1-1.  Install script overrides

VARIABLEFUNCTION
CONN_INSTALL_DIRalternate install directory
CONN_MAN_DIRalternate manpage directory
CONN_VERSIONinstall a specific release

1-3.Building from source requires Go 1.25 or later:

$go install github.com/w0zro/conn@latest

SECTION 2

First run

$conn

2-1.There is nothing to set up. conn brings up a tmux server of its own, attaches the terminal to it, and opens the navigator down the left of the session's first window. The status line at the foot is tmux's, and names the mode the keys are in. conn looks for repositories under ~/projects; the configuration (Section 8) points it elsewhere.

2-2.The list opens showing what is running, so on a quiet machine it may say nothing running. Two keys from there:

Table 2-1.  First keys

.show every repository, running or not
/find one by name

SECTION 3

The navigator

3-1.The left column is a tree, at most four levels deep: group → repository → sub-project → process. A repository is every git repository under the project roots. The scan skips node_modules, vendor, target, .build, Pods, .venv and venv, every directory whose name begins with a dot, and anything named in skipDirs.

3-2.A folder inside a root that holds two or more repositories groups them. The group is a place of its own: s opens a shell at the folder, r runs the folder's plan, x covers everything beneath it.

3-3.In a monorepo, a directory with a manifest is a project of its own and gets a row under its repository. Manifests, in the order they are trusted: .conn, Procfile, package.json, deno.json, composer.json, go.mod, Cargo.toml, Gemfile, mix.exs, pyproject.toml, pom.xml, build.gradle, build.gradle.kts. Ignored directories are skipped, and an untracked .conn still counts.

3-4.Each place lists the processes running in it, attributed to the innermost place they belong to, and named by what you would call them — npm run dev, not node — with the port beside a row that listens, npm run dev · :5173, the way an agent's row carries its model. A shell a plan or a task started is named for its entry, whatever runs in it: web, not the http.server that is web this time. Keys that shape the list:

Table 3-1.  Shaping the list

spacefold or unfold the selected node; a folded node shows +n for what it hides
-fold or unfold everything; unfolded rows also show pids
.toggle between everything and only what is running

3-5.Dim rows are processes with no shell of their own to go to: those started outside conn, and those a process in a shell started in turn — a claude's tools, say — which enter reaches only as far as the shell above them. All are listed and killable. One of them may be conn itself — the launcher become a tmux client, in the terminal it was started from — and that row says (me) in a color of its own. A row's mark says how its command ended, or that its process is unwell:

Table 3-2.  Row marks

✗in red: the command ended badly, or the process is stopped, in an uninterruptible wait, or a zombie. Beside the name, what the run said of itself and how long ago: test · 3 failed · 3m
✓in green: the command ended well — test · 12 passed · 2h

3-6.Beside the list, while the keys are in it, is the navigator's own pane: what is known about the row under the cursor, a held shell's included, with the last of what that shell has shown beneath the facts, in the colors the shell drew it in. What a process is doing can be read without entering it. A shell is placed beside the navigator only when you enter it, and goes back to a window of its own when the keys come home.

3-7./ finds places and processes: a query lists the processes that answer it — by anything their row says: the command, what it was run with, the plan's name for it, an agent's name and model, a port — under the places they run, pruned to the branches that answer. An empty query lists places alone. Up and down, or ctrl-p and ctrl-n, move the cursor through what is left, and acting on what it is on ends the looking: enter opens a shell on a place and steps into a found process's shell, ctrl-r runs the plan there, ctrl-a starts an agent, tab goes to the next thing that needs you, shift+tab back where the keys were, and ctrl-x asks to kill what the cursor is on — the filter holds, so the subject stays listed. esc abandons the look and puts the cursor back on the row it left. The query takes readline's editing keys — ctrl-w, ctrl-u, ctrl-h, ctrl-e and the rest.

3-8.Matching is fuzzy: each word of the query appears in order, not contiguously — tsl finds tressle-api, mono api finds the api inside mono — and the letters that matched are lit in the rows.

3-9.n makes a new project. It asks where on the status line, on a line prefilled with the folder the cursor is in relative to its root — w0zro/ for a cursor on a repository in that folder, nothing for one at the root — and the name goes on the end: backspace the folder away for the root itself, or type another folder, which is made if it is not there. A path from ~ or / is taken as it is. enter makes the directory, runs git init in it, and opens a shell there; the cursor lands on the project once the scan lists it. A directory already there is left alone, and esc thinks better of it.

SECTION 4

Shells

4-1.s opens a shell at the selected place, beside the navigator, and puts the keys in it. enter on a shell's row does the same for that shell. From then on every keystroke is the shell's: the pane is tmux's, and it behaves the way a tmux pane behaves, with the navigator still down the left. conn keeps one key: ctrl-space, the prefix — tmux's own, bound by conn's configuration — which reaches conn from any shell. ctrl-space - is back to the navigator; ctrl-space j and k are the next and previous shell; ctrl-space ctrl-space is back where the keys were — the shell before this one, whether or not the navigator was the way there, or the navigator when they came from there; again returns. ctrl-space q leaves, and ? — in the navigator, or after the prefix from any shell — lists the rest in a popup over the whole window. Every key tmux would otherwise bind is unbound.

4-2.A shell you enter moves in beside the navigator; when the keys come home it moves out again, to a tmux window of its own, where it keeps running, and the navigator has the whole window. J and K step through the shells in the list's order, keys and all.

4-3.The status line at the foot is tmux's. It begins with conn's own name, CONN, in purple, which stays. To its right is the mode the keys are in — NAV or PROC for the pane that has them, each a chip in its own color with the line washed one tone after it; PREFIX while a chord hangs; COPY in copy mode; the query while one is typed and the filter while one stands; CONTINUE with the picker open; NEW with a project's name being typed; CONFIRM while a kill waits on its second key — and then anything the navigator has to say: a report, an error, a confirmation, until the next key, or that a newer conn is out, whenever nothing else is said. What a chord says, from any shell, shows there too, for a few seconds. The right corner names the kind of agent a starts.

4-4.Shells keep running when the terminal closes. q in the navigator, or ctrl-space q anywhere, detaches; quit the terminal, come back, run conn, and everything is where it was.

4-5.The mouse is tmux's, with tmux's own bindings and nothing of conn's: the wheel scrolls back through a pane's transcript — each shell keeps 10,000 lines of it by default, and scrollback in the configuration raises that — a drag selects and copies to the clipboard on release, a click takes the keys to the pane under it, and a program that speaks mouse gets its own clicks and wheel. Hold shift to drag a selection the terminal's own way. A program that copies for itself — vim's clipboard yank, anything speaking OSC 52 — reaches the system clipboard through tmux.

NOTE

A click into the navigator brings the keys home the way ctrl-space - does: the shell beside it goes back to its own window, and the navigator's pane returns.

SECTION 5

Agents

5-1.a starts an agent in the selected place, in a shell like any other — Claude Code by default; the configuration's agent setting selects another. Claude Code reports its state, shown as a mark in the navigator:

Table 5-1.  Agent marks

⠇turning: the instance is working
◆blocked mid-turn on something specific: a permission prompt, a question
●finished its turn; waiting for what you ask next
○idle since it started

5-2.The mark tells you, from across the list, which projects need attention — the ◆ most of all, since answering it resumes work already underway. The pane for a Claude row names what a blocked instance is waiting on, the last thing asked of it, and what it says it is doing.

5-3.ctrl-space enter goes to the next thing that needs you, from any shell: an agent waiting, a command that ended badly, a process stopped or a zombie. Pressing it again continues around them in turn; tab does the same at the list. A held shell is entered, where the ask or the transcript is; a process conn only watches gets the cursor.

5-4.A conversation does not end when its instance exits; it is suspended, and the transcript is enough to pick it back up. A on a place lists what is suspended there — sub-projects included — newest first: when each conversation last moved, its branch, and the last thing you asked of it. Letters narrow the list the way the filter does, enter continues the one under the cursor in a shell opened where the conversation was had, and esc closes the list. A conversation an instance is still carrying is not offered. Every kind that keeps conversations answers the picker, and each is continued by the kind that had it.

SECTION 6

Plans and tasks

6-1.Working on a project usually means the same processes every time: the dev server, the test watcher, an agent. A project lists them in .conn — Procfile format, one name and command per line:

dev:   npm run dev
api:   go run ./cmd/api
agent: claude

Figure 6-1.  A plan, in Procfile format

6-2.Without one, conn reads the conventions in this order: a Procfile means every line is a process; a package.json contributes only its dev or start script, whichever exists first; a compose file contributes compose: docker compose up, one entry, since compose runs every service and attaches to each.

6-3.r starts the plan's entries that are not running, each in its own window named for its entry, and puts the cursor on the first of them. It is a list to run, not a supervisor: nothing restarts on its own. When an entry's command ends, its shell stays at the prompt with the transcript: the row wears ✗ in red if the command ended badly and ✓ in green if it ended well, the checklist in the place's pane shows the entry down with how and when it ended, and r starts it again beside the old shell. Running anything in that shell by hand clears its mark: the ending was acted on.

6-4.t, b and l run the place's tests, its build and its lint, the way the place already says they run. What the project wrote down for the purpose comes first; otherwise the ecosystem's own command, by the file that marks the project. Only a linter the ecosystem ships with is guessed at; a project on ruff or eslint names it in a script. A project the guess is wrong for says so in its Makefile, which conn believes first.

Table 6-1.  How a task's command is found

THE PROJECT HASTHE TASK RUNS
Makefile, justfile, Taskfilethe target, recipe or task named test, build or lint
package.jsonthe script named for the task, run with npm
go.modgo test ./..., go build ./..., go vet ./...
Cargo.tomlcargo test, cargo build, cargo clippy
pyproject.tomlpytest; python3 manage.py test for a Django project
Gemfilerspec with a spec directory, else rake test
mix.exs and the restthe ecosystem's own commands: mix, gradle, mvn, deno, swift, dune

6-5.Each run is a shell named for its task, so its row wears the check when it ends well and the cross when it fails, tab goes to a failure, and the place's pane says how each task's last run went and how long ago. The key again replaces a finished run rather than stacking another beside it; a run still going is left to finish. conn test, conn build, conn lint and ctrl-space t, b, l do the same from any shell.

6-6.conn reads the end of the transcript the way you would, by the shape of the tool's summary line — go test, pytest, jest, vitest, mocha, cargo, rspec, ExUnit, golangci-lint, tsc, ruff, eslint — so a failed run's row says test · 3 failed and a passed one 12 passed. A shape it does not know leaves the status alone.

NOTE

A plan is not a supervisor; nothing restarts automatically. An ended entry's shell stays at its prompt, with its transcript, until x closes it or r starts the entry again beside it.

6-7.A project on docker runs its services in containers, and a container is not a process the scan can see: on macOS it runs in docker's own machine, and on Linux it is root's, working in a directory of its own. docker knows, and compose writes on every container it starts the directory it was started for — the same fact lsof reports of a process — so a container is filed under its place by the rule everything else is, in a row named for its service with the ports it publishes on the host: web · :8438. It sits under the docker compose up that runs it when one runs in a shell, and under the place itself when compose was left detached. The row has no shell to enter; its pane says the container's name, image and status, with the last of its logs, and x asks docker to stop it. What x stopped, r brings back, where it was: the services the place's compose declares are what compose says it needs, and r starts the ones that are down with docker compose up -d for them — which starts a stopped container and makes again one that was removed — and the compose up running in a shell there takes the service's logs up again, so the shape holds: the service under its entry, as it was. Unless an entry r is starting runs compose itself, which brings up everything at once. A container without a directory — started by hand, or by something other than compose — belongs to no place and is not listed, the way a process working outside every project is not. Without docker, or with its daemon down, nothing is asked.

SECTION 7

Killing

Table 7-1.  Kill keys

xkill the selected process
Xkill it and everything under it
x on a repository or groupkill everything running in it

7-1.Every kill asks first — x, y or enter confirms; anything else cancels. Processes get SIGTERM, and a signalled row wears a red marker until a rescan actually observes the exit; the list never claims an exit it has not seen. Kills work on any listed process, including ones conn did not start. A shell conn holds is closed through the server — but one still running its command is closed only once the command has gone: what runs in the shell gets SIGTERM first, and the shell goes when a scan finds it back at its prompt, so a docker compose up stops its containers on the way out, which hung up it would not.

SECTION 9

The server

9-1.The shells live in a tmux server of conn's own, one per user for all projects, on a socket at ~/.local/state/conn/tmux-<uid>.sock; CONN_SOCKET overrides, and XDG_STATE_HOME moves the directory. Every conn writes the server's configuration — the prefix and its chords, the status line, the transcript cap — to ~/.local/state/conn/tmux.conf, brings the server up under it or sources it into one already running, and attaches. No .tmux.conf reaches it. The session's first window is the home window: the navigator in the pane down its left, at the configuration's navWidth through every resize, and the shell the keys are in beside it; with the keys in the navigator, the pane is its own, and every shell waits in a window of its own.

9-2.Close the navigator and ctrl-space - makes it again, on the left. A conn from a newer build than the navigator's restarts the navigator in its pane, the way it re-reads the configuration: the server keeps the shells, and everything else is the build's. Run from a shell inside the window, it does that and no more, the terminal being attached already; inside any other tmux it refuses, since attaching would be nesting.

9-4.conn keeps itself current. The navigator asks github which release is latest — on its first paint and once a day after, a plain request for the release page's redirect, the answer kept in ~/.local/state/conn/latest-release so a navigator started again is not another ask — and a release newer than the build says so on the status line whenever nothing else is being said: conn 0.5.0 is out · U installs it. U runs the installer in a popup over the window, aimed at the directory this build runs from, and then conn, which gives the server the new configuration and brings the navigator back as the new build; the shells stay. With nothing newer known, U asks now and says what it finds. A build that is no release — a tree past a tag, a plain go build — is never behind one. Upgrading by hand does not touch the server either: install the new binary, and the next conn sources the new configuration into the same server and replaces the navigator when the build changed. R ends the server and every shell it holds, after asking; it is the way to a fresh server when one is wanted. conn restart, typed at a terminal outside the window, is R and then conn as one command; inside the window it refuses, since the pane running it would go with the server. tmux -S ~/.local/state/conn/tmux-<uid>.sock attach is what conn does.

9-5.conn ls is the same state for scripts. The exit is how the command a shell was started with ended, and is empty while it runs. No server listening is an empty list, not an error.
