SECTION 1

General

1-1.conn is a terminal UI for working on many projects at once. It knows every git repository under your project roots and what is running in each, and it treats a process the way an editor treats a file: every shell, agent, task and container log it holds is a buffer, the buffers open are the tabs across the top of the window, and the ones that need you are marked.

1-2.conn is one window. conn's own pane runs across the top, two rows: the tabline, and the heading of the buffer shown. The buffer with focus fills the window under it; the tmux status line sits at the foot. The other buffers keep running out of view until you step back to them. Close the terminal and everything keeps running; run conn again and it shows what it showed.

1-3.Install the release built for this machine:

$curl -fsSL https://conn.w0zro.com/install.sh | sh

1-4.The script checks the download against the release's checksums, puts the binary in ~/.local/bin and the manpage under ~/.local/share/man. man conn is this manual.

SECTION 2

The window

2-1.The tabline is the working set: one tab for every buffer conn holds — the shells it opened, the agents, the tasks, a plan's entries, a container's logs — named place/name and nothing more: conn/claude, datum/tests, pg — the facts live in the heading. The tab with focus is bold ink on the ground, with an orange rim under it on the row of air beneath the tabs, teal under the everything view's; the others are gray on the bar. Each tab carries its buffer's mark (Table 2-1), and the mark stays while the state does. Two buffers that would read the same are told apart by the shortest fact that differs, in gray: the branch, when both are known and differ, else an ordinal, conn/claude ·2, only while the collision lasts. The right end holds one hint for the moment: ⌃spc p opens, r reruns, esc keeps it, . toggles running · all.

Table 2-1.  Marks, on a tab and on a row

⠇in amber: working — an agent mid-turn
◆in owed orange: an ask owed — a permission prompt, a question
●in green: done, with a result you have not looked at yet; looked at, the mark goes hollow
✓in green: the command ended well. Beside the name, what the run said of itself and how long ago: test · 12 passed · 2h
✗in owed orange: the command ended badly, or the process is stopped or hung: test · 3 failed · 3m
⬢in teal: a container

2-2.Under the tabline is the heading of the buffer shown: its name, bold in parchment, then its facts in gray, joined by middots. in <place>; the command a task ran; its pid; the ports it listens on; an agent's branch and the size of its context, 48.2k tokens, read from its transcript; how long a waiting agent has waited, waiting 3m. For a run that ended, how, in the mark's color: ✗ exit 1 · 3 failed · 2m ago, or the same after ✓; then its past runs from the record (Appendix B), newest first: past runs ✗ 2m ✓ 12s ✓ 14s. What a buffer is doing is read off its heading.

2-3.. at conn, or ctrl-space - from any buffer, is the everything view: every process, grouped by place, drawn by conn in the whole window under the tabline, where an everything tab stands first. It is two levels deep: a heading for every place, at the margin, and its rows one indent in. A repository under a group is named for both, w0zro/conn; a sub-project for its repository and itself, conn/docs; a group is a heading only for work at its own level. A group, a repository and a sub-project are each a place: a row you can open a shell at. A repository is any git repository under a root. conn skips node_modules, vendor, target, .build, Pods, .venv, venv, every directory whose name begins with a dot, and whatever skipDirs names.

2-4.A folder inside a root that holds two or more repositories is a group. It is a place of its own: s opens a shell there, r runs its plan, x covers everything beneath it.

2-5.In a monorepo, a directory with a manifest is a sub-project and gets a row under its repository. A manifest is any of .conn, Procfile, package.json, deno.json, composer.json, go.mod, Cargo.toml, Gemfile, mix.exs, pyproject.toml, pom.xml, build.gradle or build.gradle.kts. Directories git ignores are skipped; an untracked .conn still counts. A process working in a directory with a manifest is listed under it either way: the process makes the sub-project, and the manifest names it.

2-6.Each place lists what is running in it, named by what you would call it: npm run dev, not node. A row that listens carries its port, npm run dev · :5173; an agent's row carries its model; a container's row its mark and its age, ⬢ pg · :5432 · up 2d; a shell a plan or a task started is named for its entry; a row that ended or is stuck carries the mark of Table 2-1. Place headings are bold in parchment; the cursor's row is a bar on the chip's ground with an orange ▸ in its gutter, and keeps its colors — hue never says where the cursor is, the bar does; a folded place says what it hides, +3 folded. Faint rows have no buffer to step into: processes started outside conn, and processes a shell's command started in turn, a claude's tools, say; the view says so of them, dim means look, don't step. enter reaches as far as the shell above them. All are listed and killable. The row that is conn itself says (me). The newest conversation at rest under a place with work is a row of its own, claude · suspended · 6h (5-3); what runs outside every project is under global (6-5). The foot of the view teaches two lines of keys; with nothing running it says nothing running and names the doors (1-6).

2-8.The mouse works throughout: the wheel scrolls back through a pane, a drag selects and copies on release, a click focuses the pane under it, and a program that uses the mouse gets its own clicks and wheel. 2-9.conn draws in truecolor with a palette of its own, the hangar (Table 2-3). Hue is spent on state and focus alone, one accent to a phrase. SECTION 4

Shells

4-1.s on a place in the everything view, enter on a place in the finder, or ctrl-space s from a buffer, opens your shell at the place: a buffer, with a tab in the tabline, focused, filling the window. When another buffer takes focus it moves out of view, where it keeps running, and its tab stays. Each shell keeps 10,000 lines of scrollback; scrollback in the configuration raises that.

4-2.The finder makes projects. A query that matches nothing is offered as a name: enter on w0zro/parser makes w0zro/parser under the first projects root, folder and all, runs git init in it and opens a shell there, and the project is listed from then on. A directory already there is left alone. esc closes the finder instead.

4-3.e on a buffer, or ctrl-space e from any pane, is the environment, annotated: a popup over the window, headed <name>'s environment · pid 4402 · 61 variables, 6 telling. The process is the one the pane is running — the dev server, not the shell that started it — and the variables are the ones it was started with; a shell at its prompt shows what it started with, and an export typed since is not there. The telling variables come first: the *_ENV family, PORT and HOST, LOG_LEVEL, URLs and DSNs, VIRTUAL_ENV; each is NAME=value, the name in teal, and after a ← in gray what conn read from it, ← where it listens: in owed orange when the value looks wrong, ← nothing is listening, in amber when it looks suspicious, a venv from another project. Each is read for what it is. A path says whether it is there; PATH is counted, its missing and repeated entries marked, and the place's tools found along it. A URL or a port that points at this machine says who is listening there, or that nothing is. Secrets are never listed; a password in a URL is masked •••. space unfolds all N variables, grouped by who set them: the project's — the ones its .env sets, a variable the file names that the process lacks being a line of its own — then the runtime's, npm's, conn's, the shell's rc files, the terminal conn was attached from. For a variable a startup file set, the page says which file and line: it starts the shell once more, traced, after its first paint, and reads the assignment off the trace; a variable the trace did not see set is looked for in the startup files by name, and said to be named there. An entry of PATH that /etc/paths put there says so. / finds, esc closes. On a place the page is the server's environment, which every shell starts from: the terminal's, brought over each time one attaches, so a variable its rc files stopped exporting is gone from the next shell opened. conn env typed at a prompt shows that shell's environment as it is now, exports and all, since the command inherited it. On macOS a system shell at its prompt keeps its environment to itself; the page says so and shows what the shell started from, and conn env typed there shows its own.

SECTION 5

Agents

5-1.a on a place in the everything view, ctrl-a in the finder, or ctrl-space a from a buffer, starts an agent at the place, in a buffer like any other: Claude Code, unless the configuration's agent says otherwise. Claude Code reports its state, and its transcript says whether it has answered since it started, so a finished turn is read from the instance rather than remembered by the window, and stands across a restart of conn; conn marks each instance, on its tab and on its row:

Table 5-1.  Agent marks

⠇working
◆blocked mid-turn: a permission prompt, a question
●finished its turn; waiting for the next ask
○idle since it started

5-2.The ◆ is the one to answer first: answering it resumes work already underway. The answer is typed in the buffer itself, at the agent's own prompt, and the mark clears when the instance says the ask is answered. A waiting instance's heading says how long it has waited, waiting 3m, beside its branch and the size of its context; the finder's row for it says the last word. The status line counts the asks owed while any is. tab, or ctrl-space enter from any buffer, goes to it (3-8).

5-3.A conversation does not end when its instance exits; it is suspended, and can be picked back up. The newest conversation at rest under each place is a row of the finder, datum · resume, with the last thing asked of it, how long it has rested and its branch; enter continues it in a buffer opened where it was had. A on a place at conn, or ctrl-space A from any buffer, opens the finder on every conversation at rest in that place instead — the row's, or the buffer's — newest first, for the one that is not the newest. In the everything view the same conversation is a row of its own, dimmed, at the end of the place's family, claude · suspended · 6h, and enter on it continues it. A conversation an instance still carries is not offered. A place with no work shows none there: the row is kept the way an exited container is kept beside its running siblings.

5-4.conn knows two kinds of agent: claude and ollama. , at conn or in the finder, or ctrl-space , from any buffer, moves a on to the next kind, around the end, for every window until conn is restarted; the finder's foot names it, ^a a claude here. Ollama's rows are plain processes, unmarked. It runs the model most recently pulled or run; with nothing pulled, a runs ollama list instead, and with the ollama server down the REPL says so. agentRuns in the configuration names what a kind runs when its own choice is not the wanted one.

SECTION 6

Plans

6-1.Working on a project usually means the same processes every time. A project lists them in .conn, Procfile format, one name and command per line:

dev:   npm run dev
api:   go run ./cmd/api
agent: claude

Figure 6-1.  A plan

6-2.Without one, conn reads the project's own files, in this order:

Table 6-1.  Where a plan comes from

.connevery line is an entry
Procfileevery line is an entry
package.jsonone entry: its dev script, else its start script
compose.yamlone entry, compose: docker compose up, since compose runs every service and attaches to each; compose.yml, docker-compose.yml and docker-compose.yaml the same

6-3.r on a place, ctrl-space r from a buffer, or enter on an entry in the finder, starts the entries that are not running, each in a buffer named for it, with a tab in the tabline, and shows the first. An entry is running when its command is running in the place, whoever started it: the shell r opened for it, a shell opened by hand, or a terminal outside conn. The command a shell was started with is kept on it, so what a shell ran is what it ran whatever the plan says since. It is a list to run, not a supervisor: nothing restarts on its own. When an entry's command ends, it says so itself as it goes, and conn hears it rather than finding the shell at its prompt on a later look; the shell stays at the prompt with the transcript, the tab and the row show ✗ or ✓, the heading says how and when it ended and the runs before it, and r starts it again beside the old shell. What the run said of itself, and that its ending is on the record, are kept on the shell, so a conn started later says the same and records nothing twice. Running anything by hand in that shell clears the mark.

6-5.What runs outside every project is listed under global, at the foot of the everything view, while there is anything to list: containers started by hand or from elsewhere, processes listening on a port from outside your projects, an ollama serve or a brew postgres, and agents started outside your projects, with what they run: an agent is yours wherever it runs, and the place is a label on it, not a gate. SECTION 7

Runs

7-1.Each entry r starts is a buffer named for it, datum/api, in a shell of its own, so its tab and its row show ✓ or ✗, tab goes to a failure, and the status line's chip says FAILED while a failed one is shown. The buffer outlives its run — dead, but readable: the transcript stays, and the heading says how the run ended and the runs before it, ✗ exit 1 · 3 failed · 2m ago · past runs ✓ 12s ✓ 14s. Stepping onto a dead buffer, by tab, h l or the finder, shows it with the keys kept at conn: r runs it again in place — the same pane, cleared, the same name; gf opens the last file:line the transcript names in $EDITOR, vi without one, in the buffer's own shell; q closes the buffer, its runs staying on the record; enter steps into the shell beneath. Running anything by hand in that shell makes it a live buffer again, and the ending clears.

7-2.conn reads the run's summary line as the tool prints it: go test, pytest, jest, vitest, mocha, cargo, rspec, ExUnit, golangci-lint, tsc, ruff, eslint. A failed run's heading says ✗ exit 1 · 3 failed, a passed one ✓ 12 passed, and its row says the same. Output conn does not recognize leaves them with pass or fail alone.

8-1.Nothing dies unasked. x shows what dying means before anything dies. In the everything view it shows it on the view itself: the processes to die carry ✗ on their rows and say about to die, the confirm line stands under the list, X kills all 3 · x the head alone · esc changes your mind, and the view keeps the window through the kill, done or kept. From a buffer it takes the window for a page of its own: the heading, <name> in <place> · about to die; the process tree with ✗ before each name, and after it the pid and the ports it holds, pid 4431 · holds :3000; the consequences in prose, the tree dies together — an orphaned esbuild is a zombie you would meet again as ✗ stopped · :3000 frees · nothing else touches it; and the same confirm line. The status line's chip says CONFIRM, and beside it the facts, conn/web · 3 processes · :3000. X takes the tree; x the head alone, the row's process and the shell around it; y or enter whichever was asked. Processes get SIGTERM; 9 confirms with SIGKILL, i with SIGINT, for a server that only tears down on ctrl-c, and h with SIGHUP, for a daemon that reloads on it. Any other key keeps everything alive and gives the buffer back, or the list. A signalled row keeps its mark until the process is seen to have gone; conn never claims an exit it has not seen. A process that has not gone in five seconds is given up on, and the status line says so; x on it then, or on a row still on its way out, offers SIGKILL: outright. Kills work on any listed process, including ones conn did not start.

8-2.After death the buffer stays as the record. A held shell running a command is not hung up: the command is signalled, and the shell sits at its prompt beneath the transcript with the ending recorded, how and when, so a docker compose up stops its containers on the way out and its buffer remains to read; q closes it (7-2). A held shell at its prompt with nothing running is hung up: a buffer of nothing but a prompt. x on an entry's row previews the entry, named, and once it is dead r starts it again. X, and x on an entry, also kill processes the command started that have since detached from it; such a process is listed under the command while it runs, and the preview says orphaned of it.

8-3.A container is stopped by docker, which signals the process inside it and, after a grace period, kills it. r brings the service back (6-6).

SECTION 10

Leaving, restarting, updating

10-1.q at conn, or ctrl-space q anywhere, leaves conn and returns you to the terminal; on a dead buffer q closes the buffer first (7-2), and the next q leaves. Everything keeps running: the shells, the plans, the agents. Run conn again, from any terminal, and it shows what it showed. If conn's pane was closed, ctrl-space - brings the everything view, and the pane with it.

10-2.R, or ctrl-space R from any buffer, ends conn and every buffer it holds, after asking. conn restart, typed in a terminal outside conn, does the same and then starts conn again; inside conn it stops with a message, since the shell running it would go too. A restart is the way to a fresh start, and what a raised scrollback needs to take effect.

10-3.conn checks for a newer release once a day. When one is out, the status line says so whenever nothing else is being said: conn 0.6.0 is out · U installs it. U installs it and restarts conn as the new build; the buffers stay. With nothing newer known, U checks now and says what it finds. Installing a new binary by hand works the same: the next conn picks it up. A build from source is never told it is behind.
