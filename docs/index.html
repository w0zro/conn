SECTION 1

General

1-1. conn is a station for one operator directing many processes on one machine. It runs on tmux, which it starts and holds. The panel occupies the left of the terminal and the workspace the rest. The panel lists the processes working each project — shells, contacts, and commands — with what each is doing and which is waiting on the operator. The workspace holds the one process the operator is in. Keys move between them.

1-2. A contact is a process with an agent at the other end: Claude Code, or another conn knows by name. A contact works without direction and stops to ask for it. The station shows which one has stopped, and tab goes to the one that has waited longest.

1-3. conn finds projects by walking the roots it was given: the directories named in ~/.config/conn/config.json, or in CONN_ROOTS, which is read first. A project is a repository under a root, or a folder under one that holds two or more. conn is told the roots and infers nothing; a conn that has been told nothing asks before it goes on, in a line typed into: the directories that answer what is typed are the rows, tab fills the line in with the one under the cursor, and enter takes it and writes it to the file.

1-4. The installation procedure on the cover puts the binary in ~/.local/bin and this manual beside it, where man conn finds it. conn needs tmux on the path. On macOS it also needs lsof, which is how it reads where a process is working; Linux reads /proc. Without tmux, conn shows the console and the processes view and can reach nothing.

SECTION 2

Operation

2-1. conn comes up on the console: a readout of the machine and the session, the start-up checks, and the verdict. A check that found something wrong is a fault, and the verdict counts them; with none it says so. Any key continues to the processes view; from there c brings the console back.

2-2. The processes view is what is running, by project. Each project work is happening in is a block, and each process there is a row, nested under whatever runs it. A row says its kind, what it is doing, how long it has stood as it does, and the word for how it stands. The projects are in the order of their paths, as the list has them. Within one, nothing moves once placed: what is new goes on the end. A row conn holds in a pane of its server is written in the ink and can be entered; work conn can only report is dimmed. At rest the view is quiet: a tree shows its head, and under it only a contact, a fault, or a row that is waiting; what else runs under a shell is said on the shell's own row. z shows the whole tree, and the status line says TREE while it does.

Kinds

KINDWHAT THE ROW IS
SHELLA shell. Bare, it is idle; running anything, it is active as what it runs is.
CONTACTAn agent, and the one kind that can wait on the operator.
EDITORAn editor.
RUNAnything else: a build, a test, a server, a script.
SERVICEA docker container, filed under the project compose started it for.

Words

WORDHOW THE ROW STANDS
WORKINGDoing something now. A contact says what: the tool it has in flight.
WAITINGA contact stopped on a question it put to the operator.
ACTIVEAlive, and not doing anything.
IDLEA shell at its prompt, or a contact at rest.
STOPPEDSuspended.
ENDEDFinished, and not yet collected.
DOWNDeclared in the project's .conn, and not running.
EXIT nEnded with that code: a service, or a declared process. A fault.
UNHEALTHY, RESTARTING, STARTINGA service, as docker says it stands. The first two are faults.

2-3. While the keys are on the panel, the workspace holds the readout on the row under the cursor: the whole command, where the process is working, what runs it and what it runs, what it has spent, what a contact is stopped on, and what git says of the project. It follows the cursor. enter puts the process in the workspace instead, with the keys in it, and esc goes back into the process last worked in.

2-4. p is the projects list: every project under the roots, whether anything is running in it or not, and under each what conn has running there. Typing narrows it. The workspace holds the readout here too, on the row under the cursor: a process's own, or for a project where it is, what git says of it, and what is running in it. enter opens a shell at the row under the cursor, alt-c starts a contact there, alt-a lists the sessions a contact left suspended there, alt-u brings up what the project declares, and esc goes back. In the sessions list, enter picks the session under the cursor back up, and the workspace holds the readout on it: when it last moved, its branch, the last thing asked of it, the model, and the command that picks it back up.

2-5. x asks to end the process under the cursor, on the status line, and the question is the command conn is about to run: kill -TERM for anything a shell runs, from its own row or from the shell's row that says it; kill -KILL for a bare shell, which ignores the gentler signal; docker stop for a service; tmux's kill-pane for a pane held after its process ended. y answers yes and any other key withdraws the question, as tmux's own confirmation goes. The shell a process ran in is left at its prompt.

2-6. A service has no pane, so enter on one opens its output, and enter again goes into the pane holding that; s on one opens a shell inside the container.

2-7. A project may declare the processes that work it in a file named .conn at its path; the file's form is at 4-5. Where work is happening in the project, each declared process not running is a row at the foot of its block, dimmed and worded DOWN; a project nothing is running in shows nothing of its file. enter on such a row brings it up in a pane of the station and goes into it; u on any row of the project brings up everything it declares that is down. A pane conn opened this way carries the declared name on its head row. When the process ends the pane holds its output and the row reads ENDED, or EXIT and the code as a fault; enter goes in to read it, u opens it anew, and x closes it. A file that will not read is said under the block, with the line.

SECTION 3

Keys

3-1. A chord is the prefix — ctrl-space, or what CONN_PREFIX names — followed by one key. A chord works from anywhere in the station, including from inside a process, because tmux takes it before the process does. The status line says PREFIX while one is pending.

Chords

KEYACTION
prefix -The processes view, from wherever the keys are. Puts the manual away if it is up.
prefix pThe projects list.
prefix prefixThe process worked in before this one.
prefix tabThe process that has waited longest.
prefix jDown the processes conn can put in the workspace.
prefix kUp them.
prefix sA shell at the project the panel is looking at.
prefix aA contact at that project.
prefix alt-aThe sessions suspended at that project.
prefix ?This manual, in the workspace, with the keys in it.
prefix qDetach. The station keeps running.

3-2. The panel's own keys work while the panel has them, and are listed here as the processes view takes them. In the projects list and the sessions list a letter is typed into the line instead, and the line is edited with readline's keys: there, enter takes the row under the cursor and esc goes back.

The panel

KEYACTION
j, kDown and up the rows.
g gThe first row.
GThe last row.
zThe whole tree, and the quiet view again.
enterInto the process under the cursor. On a service, its output; enter again goes into the pane holding it. On a declared process that is down, brings it up.
escBack into the process last worked in.
sA shell at the project. On a service, a shell inside the container.
aA contact at the project.
xEnd it: a signal to a process, docker stop to a service, and on a declared process that has ended, close its pane. Asks first.
uBring up what the project declares and does not have running.
tabThe process that has waited longest.
pThe projects list.
cThe console.
qDetach.

3-3. While this manual is up the keys are in it, and the status line says HELP. It scrolls with j and k, a screen at a time with space and b, and to either end with g and G. esc leaves it and puts the keys back where they were when it was asked for — in the workspace, or on the panel; prefix - leaves it for the processes view whichever it was.

SECTION 4

Commands and configuration

4-1. conn is called as follows. A second conn, run while the station is up, attaches to it.

COMMANDACTION
connThe console, then the processes view.
conn downTake the server down, with everything in it.
conn theme claudeWrite conn's palette as a theme for Claude Code, which draws its own colors.
conn theme vimWrite it as a colorscheme for nvim, which does the same.
conn --lightSay the ground is light, for a server coming up or one already up.
conn --darkSay the ground is dark.
conn --helpSay this.
conn --versionSay the build.

4-2. conn comes up dark, or light when the terminal says its own ground is light. The choice is made when the server comes up and holds for its life; conn down and conn again asks afresh. Everything in a pane of the server draws in conn's palette by asking the terminal for a color by name. Claude Code and nvim write their own hex instead, and conn theme writes each a theme from the same palette.

4-3. The configuration file is ~/.config/conn/config.json. It holds one key.

KEYVALUE
rootsThe directories conn looks for projects under, as a list of paths. A leading ~ is the home.

4-4. The environment says what one run of conn should do differently from what the file says is usual.

VARIABLEVALUE
CONN_ROOTSThe roots for this run, separated the way PATH is. Read ahead of the file.
CONN_PREFIXThe prefix, in tmux's spelling. C-Space unless set.
CONN_SOCKETThe socket of the server, for a second station on one machine. Under ~/.local/state/conn unless set.

4-5. A project's .conn declares the processes that work it, one a line, as name [dir]: command. A line beginning with # is a comment. A line that will not parse is said under the project's block with its number, and nothing is guessed at in its place.

PARTMEANING
nameOne word of letters, digits, dots, dashes and underscores, and the row's label.
dirWhere the pane opens, under the project. Left out, the project itself.
commandA shell line, run as written.
# .conn
web frontend: npm run dev
api: go run ./cmd/api
worker services/queue: make run
