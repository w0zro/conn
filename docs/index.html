SECTION 1

General

1-1.PURPOSE. This manual describes conn and its operation.

1-2.SCOPE. The station serves one operator directing many processes on one machine. It shows the processes running in each project, what each is doing, and which one is waiting for the operator, and it puts the operator in front of any of them. It does not edit files, run builds, or hold sessions. The processes do.

1-3.DEFINITIONS. Terms used in this manual.

OperatorThe person using conn.
ProcessA shell, a contact, or a command a shell is running. The unit the station lists and reaches.
ContactA process connected to a non-human intelligence: Claude Code running in a terminal. It works a project and can stop to wait for the operator.
IntelligenceThe non-human intelligence at the other end of a contact. The station sees the contact and not the intelligence.
SessionThe conversation a contact carries, from raising it to ending it. Its record is the transcript. A session outlives its contact and can be resumed.
ProjectThe directory a process runs in: a git repository, or a folder that holds several repositories.
StatusThe state the station reports for a process: WORKING, ACTIVE, IDLE, or WAITING.
WaitingThe status of a contact that has stopped and needs an answer from the operator, such as a permission or a question.
ConsoleThe page conn comes up on. It reads out the machine and gives a verdict.
PanelThe left pane of the window, forty-four columns wide. It shows one of the three views and usually holds the keys.
ProcessesThe view listing every process at each project, in the order they started.
ProjectsThe view listing every project under the roots, running or not.
SessionsThe view listing the sessions at a project that can be resumed.
BayThe right pane of the window. It holds one process.
ReadoutA page of labeled values on one process, shown in the bay.
Status lineThe line at the bottom of the window. It shows where the keys are, on the left.

1-4.INDICATIONS. The station indicates two things: what each process is doing, and which process is waiting. The processes view shows both: the status column shows the first, and the word WAITING, blinking, shows the second. tab goes to what is waiting from anywhere in the server (4-3).

1-5.COMMANDS. The command alone brings up the console and continues to processes. Other commands are given by name after it. --light and --dark set the ground, ahead of a command if one is given.

SYNOPSIS

COMMANDDOES
connBrings up the console, then processes.
conn downTakes the server down with everything in it, and reports what went.
conn theme claudeWrites conn's theme for Claude Code.
conn theme vimWrites conn's colorscheme for nvim.
conn --lightSets the ground light.
conn --darkSets the ground dark.
conn --helpPrints this table.
conn --versionPrints the build.

SECTION 2

The Station

2-1.ARRANGEMENT. The station is one window of a tmux server that conn holds. The panel is on the left and the bay on the right. The status line runs under both. Figure 2-1 shows the arrangement.

┌──────────────────────────────┬─────────────────────────────┐
│ PANEL                        │ BAY                         │
│                              │                             │
│ KIND     COMMAND  AGE STATUS │ The process reached from    │
│                              │ the panel: a shell, a       │
│ w0zro/conn                   │ contact, a run, or the      │
│ SHELL    zsh      2H    IDLE │ readout. The keys are here  │
│▸ CONTACT claude   1H WAITING │ while a process is.         │
│                              │                             │
├──────────────────────────────┴─────────────────────────────┤
│ STATUS LINE  PROCS                                         │
└────────────────────────────────────────────────────────────┘

FIGURE 2-1. STATION ARRANGEMENT

2-2.THE SERVER. The station holds a tmux server of its own. Its socket is under ~/.local/state/conn, or where CONN_SOCKET says. The first conn brings the server up and puts the terminal on it. A later conn attaches to what is there. Everything in the server stays until the server is taken down (5-2). A process that leaves the bay goes to a window of its own, out of sight, and keeps running.

2-3.COMING UP. To bring up the station:

1.Type conn.
2.The console comes up. It reads out the machine, runs the start-up checks, and gives its verdict: ALL SYSTEMS NOMINAL, or the count of systems that are not.
3.Press any key. The processes view comes up on the panel and the bay opens beside it.

2-4.THE CONSOLE. c in the processes view brings the console back over the whole window. Any key returns to processes.

2-5.THE PREFIX. Chords are given under ctrl-space. CONN_PREFIX names another prefix, in the spelling tmux uses. While a chord is open, PREFIX is lit on the status line. No other tmux key is bound.

CHORDDOES
ctrl-space -Puts the keys on the panel, from anywhere in the server.
ctrl-space pOpens projects, from anywhere in the server (3-7).
ctrl-space tabGoes to the contact that has waited longest (4-3).
ctrl-space ctrl-spaceGoes to the process that was last in the bay (4-4).
ctrl-space qDetaches (2-6).

2-6.STANDING DOWN. q on the panel detaches the terminal from the server. ctrl-space q does the same from anywhere in it. The server and every process in it keep running, and the next conn attaches to them. Ending the server is procedure 5-2.

2-7.WITHOUT TMUX. Without tmux on the path, the station shows the console and the processes view and reaches nothing. On macOS the processes view needs lsof to read the working directory of a process.

2-8.THE GROUND. The server comes up on a dark or a light ground. The first time it rises it asks the terminal for its background and keeps the answer for the life of the server. conn --light and conn --dark set the ground instead, for a server coming up or one already up. Every pane takes the new ground.

2-9.THEMES. A program that draws its own colors takes none of the server's. conn theme claude writes a theme for Claude Code and offers to select it. conn theme vim writes a colorscheme for nvim, taken with colorscheme conn. Each is drawn on the ground the server is on.

2-10.ENVIRONMENT. The station reads three variables.

VARIABLESAYS
CONN_ROOTSThe roots the projects view walks for repositories, as a path list. ~/projects when unset.
CONN_SOCKETWhere the server's socket is.
CONN_PREFIXThe prefix for chords, in the spelling tmux uses. C-Space when unset.

SECTION 3

Process Procedures

3-1.PROCESSES. The processes view lists every process at each project. A project is titled by its path below the root; a project outside every root is written from ~. Under a project the processes are shown as a tree: a shell, and what it runs indented under it. Each row shows the kind, the command, the age, and the status. On the console, which is wider, the terminal is shown too. A row keeps its position for as long as its process lives, oldest first, and a new row goes on the end. With nothing running the view says NO PROCESSES.

3-2.STATUS. The last column of a row is its status.

STATUSMEANS
WORKINGDid something between one reading and the next. A contact is WORKING when it is mid-turn, or when a command is running under it.
ACTIVEAlive and doing nothing.
IDLEA shell at its prompt, or a contact whose turn is over. Nothing is pending.
WAITINGA contact stopped on something it needs from the operator. The word blinks.
STOPPEDSuspended. Shown as a chip.
ENDEDFinished and not yet collected. Shown as a chip.

3-3.WHO IS WAITING. Only a contact that reports its own status is ever WAITING. Claude Code reports it, and reports when its status changed. A contact the station cannot ask reads as WORKING or ACTIVE from the processor time it spends.

3-4.KEYS. The cursor is on one row. It follows its process from one reading to the next.

KEYDOES
j, kMove the cursor. The arrows do the same.
enterPuts the process under the cursor in the bay, with the keys in it.
tabGoes to the contact that has waited longest (4-3).
sOpens a shell at the project under the cursor.
aRaises a contact at the project under the cursor (4-2).
alt-aOpens sessions for the project under the cursor (4-5).
iOpens the readout on the row under the cursor. Pressed again, closes it (3-6).
xAsks to end the process under the cursor (4-6).
pOpens projects (3-7).
cBrings the console back over the window (2-4).
qDetaches (2-6).

3-5.HELD AND REPORTED. A row the station holds a pane for is in the ink, and enter reaches it. A row the station can only report, a terminal it did not open, is dimmed. The cursor lands on it; no other key acts on it. The row in the bay carries its kind in orange. Outside the server every row is reported.

3-6.THE READOUT. The readout is a page of labeled values on one process, shown in the bay. It carries what the row has no room for: the whole command, the directory, the time up and the processor time spent, what runs it and what it runs; of a contact, the session it carries and what it is stopped on; of the project, what git reports. To read a row:

1.Put the cursor on the row.
2.Press i. The readout opens in the bay. The keys stay on the panel.
3.j and k move the readout with the cursor. tab carries it to the contact that is waiting.
4.Press i again. The readout closes. Where the row is one the station holds, its process takes the bay.

NOTE

conn readout 1234, from a shell in the server, pins the readout to one process instead of the cursor.

3-7.PROJECTS. The projects view lists every project under the roots, whether anything is running in it or not. A folder that holds several repositories is a row with them under it. To open a process at a project:

1.Press p in the processes view, alt-p from any view, or ctrl-space p from anywhere in the server.
2.Type to narrow the rows. backspace and ctrl-u edit the line. The arrows, or ctrl-p and ctrl-n, move the cursor.
3.Press enter. A shell opens at the project, and processes returns with it in the bay. ctrl-a raises a contact there instead (4-2). alt-a opens sessions (4-5).
4.esc returns to processes with nothing opened.

3-8.THE STATUS LINE. The status line is dark at rest. The left says where the keys are, as a block of the orange with the word knocked out of it. Every indication below wears the same block; the word says which. It is dark while the keys are in the bay, and dark on the console. The right is empty.

INDICATIONMEANS
PREFIXA chord is open. The next key is one of 2-5.
COPYThe pane with the keys is in copy mode.
CONFIRMA kill is armed. The question stands beside it (4-6). It covers the word for the view.
PROCSThe keys are on the panel, in the processes view.
PROJECTSThe keys are on the panel, in projects (3-7).
SESSIONSThe keys are on the panel, in sessions (4-5).

SECTION 4

Contact Procedures

4-1.CONTACT. A contact is a process connected to a non-human intelligence. The station raises Claude Code, and the procedures of this section are written for it. The station sees the contact and not the intelligence: what it lists, reaches, and ends is the process. A contact the station did not raise is a process like any other: it is reached, put in the bay, and ended the same way. The station cannot ask it its status, so it is never WAITING.

4-2.RAISING A CONTACT. To raise a contact at a project:

1.In the processes view, put the cursor on any row of the project. Or open projects (3-7) and put the cursor on the project.
2.Press a. In projects, press ctrl-a.
3.A shell opens at the project running claude, takes the bay, and has the keys. Its row is in the processes view under the project, kind CONTACT.
4.The station tells the contact where it is: that it runs in a pane of the station, and how to start anything long-lived in a window of its own. A process started that way has a row and can be reached.

NOTE

What the station tells the contact travels with conn. Nothing is written into the settings of Claude Code.

4-3.ANSWERING A CONTACT. When a contact stops on something it needs from the operator, its row reads WAITING and the word blinks. To answer it:

1.Press tab in the processes view, or ctrl-space tab from anywhere in the server.
2.The cursor goes to the contact that has waited longest. Its pane takes the bay and the keys land in it.
3.Answer it.
4.Press tab again for the next, longest first, and round again from the end.

4-4.WORKING TWO PROCESSES. ctrl-space ctrl-space goes to the process that was last in the bay, and pressed again comes back. A vacant bay and the readout are not remembered. alt-o does the same from the panel.

4-5.RESUMING A SESSION. A session outlives its contact. Its transcript is kept, and a new contact can resume it. To resume one:

1.In the processes view, put the cursor on any row of the project. Or open projects and put the cursor on the project.
2.Press alt-a. The sessions view lists the sessions at the project, newest first, each by its branch, the last thing it was asked, and its age. Type to narrow the rows.
3.Press enter. A shell opens running claude --resume on that session and takes the bay.
4.esc returns to processes with nothing resumed.

NOTE

A session a live contact is carrying is not listed. The sessions view checks the process table as well as the transcripts.

4-6.ENDING A CONTACT. To end a contact:

1.Put the cursor on its row and press x.
2.CONFIRM lights on the status line, with the question beside it: END CLAUDE 1234 · X CONFIRMS · ANY OTHER KEY CANCELS.
3.Press x, y, or enter. The contact is asked to end. The shell it ran in is left at its prompt. Any other key cancels.
4.The processes view reads again after a beat, and the row goes when the contact has.

NOTE

A contact ended this way keeps its session. Procedure 4-5 resumes it.

SECTION 5

Emergency Procedures

5-1.A PROCESS THAT WILL NOT END. x sends the process under the cursor SIGTERM. A bare shell is sent SIGKILL instead. A process that ignores SIGTERM stays in the processes view. Reach it with enter and end it from inside.

5-2.TAKING THE STATION DOWN. To end the server and everything in it:

CAUTION

conn down ends every process in the server: every shell, every contact, and every run, in the bay or out of sight in a window of its own. Work that is not saved is lost. A session can be resumed afterward (4-5). A run cannot.

1.From a terminal outside conn, or from a shell in it, type conn down.
2.A line is printed for each window ended and one for the server.

5-3.THE BAY EMPTIES. When the process in the bay ends, the bay takes the next process the station holds, from the cursor down and round again from the top. With none to take, it shows VACANT. Any key in it puts the keys on the panel.

5-4.THE KEYS ARE ELSEWHERE. From any pane of the server, ctrl-space - puts the keys on the panel. From the panel, enter puts them in the bay.

5-5.THE PROCESSES CANNOT BE READ. When the process table cannot be read, the processes view shows the reason as a chip in place of its rows and reads again on the next beat. On macOS the usual reason is that lsof gave no answer in time.
