SECTION 1

General

1-1.conn is a terminal UI for working on many projects at once. It lists every git repository under your project roots, what runs in each, and the shells you open there, and marks the rows that need you.

1-2.conn is a tmux client. It brings up a tmux server of its own, attaches the terminal, and runs the navigator down the left of the home window. Every shell is a tmux pane: the focused one is drawn beside the navigator, the rest wait in windows of their own. Close the terminal and everything keeps running; run conn again and it is where it was.

1-3.conn needs tmux, which holds and draws the shells, and lsof, which reads the process list. macOS ships lsof; brew install tmux. On Linux, install both from the package manager. docker is optional: with it, a project's containers are listed too (Section 6).

1-4.Install the release built for this machine:

$curl -fsSL https://conn.w0zro.com/install.sh | sh

SECTION 2

The navigator

2-1.The left column is a tree, at most four levels deep: group → repository → sub-project → process. A group, a repository and a sub-project are each a place: a row a shell can open at. A repository is any git repository under a root. The scan skips node_modules, vendor, target, .build, Pods, .venv, venv, every directory whose name begins with a dot, and whatever skipDirs names.

2-2.A folder inside a root that holds two or more repositories is a group. It is a place of its own: s opens a shell there, r runs its plan, x covers everything beneath it.

2-3.In a monorepo, a directory with a manifest is a sub-project and gets a row under its repository. Manifests, in the order they are trusted: .conn, Procfile, package.json, deno.json, composer.json, go.mod, Cargo.toml, Gemfile, mix.exs, pyproject.toml, pom.xml, build.gradle, build.gradle.kts. Ignored directories are skipped; an untracked .conn still counts.

2-4.Each place lists the processes running in it, attributed to the innermost place they belong to and named by what you would call them: npm run dev, not node. A row that listens carries its port, npm run dev · :5173; an agent's row carries its model; a shell a plan or a task started is named for its entry. Dim rows have no shell of their own to go to: processes started outside conn, and processes a shell's command started in turn, a claude's tools, say. enter reaches as far as the shell above them. All are listed and killable. The row that is conn itself says (me).

2-5.A row's mark says how its command ended, or that its process is unwell. An agent's marks are in Section 5.

Table 2-1.  Row marks

✗in red: the command ended badly, or the process is stopped, in an uninterruptible wait, or a zombie. Beside the name, what the run said of itself and how long ago: test · 3 failed · 3m
✓in green: the command ended well. test · 12 passed · 2h

2-6.While the navigator has focus, it fills the pane beside the list with what is known about the row under the cursor. For a place: its branch, status, upstream and last commit; its plan as a checklist, each entry up, down or ended and how; its tasks and how their last run went. For a process: its run, arguments, uptime, cpu, memory, state, ports and children, and beneath the facts the last of what its shell has shown, in the shell's own colors. For a container: its name, image, status and the last of its logs. What a thing is doing can be read without entering it.

2-7.tmux draws the status line at the foot. It begins with CONN in purple, then the mode (Table 2-2), then anything conn has to say until the next key: a report, an error, a confirmation, or that a newer release is out. What a chord says from a shell shows there too, for a few seconds. The right corner names the kind of agent a starts.

3-4.enter on a shell's row, or s on a place, focuses a shell beside the navigator. From then on the shell receives every keystroke but one: ctrl-space, the prefix, tmux's own under conn's configuration, which reaches conn from any shell. ctrl-space - focuses the navigator again. ?, in the navigator or after the prefix, lists every key in a popup over the window; Appendix A lists them here. Every key tmux would otherwise bind is unbound.

3-5.tab at the list, or ctrl-space enter anywhere, goes to the next thing that needs you: an agent waiting, a command that ended badly, a process stopped or a zombie. Again continues around them. A held shell is entered, at its prompt or transcript; a process conn only watches gets the cursor.

3-6.shift+tab at the list, or ctrl-space ctrl-space anywhere, returns focus to where it was: the shell before this one, whether or not focus passed through the navigator on the way, or the navigator when focus came from it. Again returns. Before focus has moved at all, it is the list from a shell and the cursor's shell from the list.

SECTION 4

Shells

4-1.s opens $SHELL at the selected place, beside the navigator, focused. A shell you enter moves in beside the navigator; when the navigator takes focus again it moves out to a tmux window of its own, where it keeps running, and the navigator has the whole window. Each shell keeps 10,000 lines of transcript; scrollback in the configuration raises that.

4-2.n makes a new project. The status line asks where, on a line prefilled with the cursor's folder relative to its root, w0zro/ for a cursor on a repository in that folder, and the name goes on the end. Backspace the folder away for the root itself; type another and it is made. A path from ~ or / is taken as it is. enter makes the directory, runs git init in it and opens a shell there; the cursor lands on the project once the scan lists it. A directory already there is left alone. esc cancels.

4-3.q in the navigator, or ctrl-space q anywhere, detaches the terminal. The shells keep running. Quit the terminal, come back, run conn: everything is where it was.

SECTION 5

Agents

5-1.a starts an agent at the selected place, in a shell like any other: Claude Code, unless the configuration's agent says otherwise. Claude Code reports its state, and the navigator marks each instance:

Table 5-1.  Agent marks

⠇working
◆blocked mid-turn: a permission prompt, a question
●finished its turn; waiting for the next ask
○idle since it started

5-2.The ◆ is the one to answer first: answering it resumes work already underway. The pane for a claude row names what it is waiting on, the last thing asked of it, and what it says it is doing. tab, or ctrl-space enter from any shell, goes to it (3-5).

5-3.A conversation does not end when its instance exits; it is suspended, and the transcript is enough to pick it back up. A on a place lists what is suspended there, sub-projects included and, for a group, its repositories, newest first: when each last moved, its branch, and the last thing asked of it. Typing narrows the list, enter continues the one under the cursor in a shell opened where it was had, esc closes the list. A conversation an instance still carries is not offered. Every kind that keeps conversations answers the picker, and each is continued by the kind that had it.

6-3.r starts the entries that are not running, each in a window named for it, and puts the cursor on the first. It is a list to run, not a supervisor: nothing restarts on its own. When an entry's command ends, its shell stays at the prompt with the transcript, the row shows ✗ or ✓, the pane's checklist says how and when it ended, and r starts it again beside the old shell. Running anything by hand in that shell clears the mark: the exit has been seen.

6-4.A project on docker runs its services in containers, which the process scan cannot see. compose writes on every container the directory it was started for, the same fact lsof reports of a process, so a container is filed under its place by the rule everything else is: a row named for its service, with the ports it publishes on the host, web · :8438. It sits under the docker compose up that runs it when one runs in a shell, and under the place itself when compose was left detached. enter on it opens a shell inside it — compose's exec, in the place — held like any shell; its pane says the container's name, image and status, with the last of its logs. A service that died beside the others stays listed while the project runs, showing the cross and how long ago — worker · 3m ✗ — and tab goes to it; one that exited well shows the check. A health check's word stands where the ports would while it says anything but healthy: api · unhealthy ✗, or starting. What the machine runs for you outside every project is listed under global, at the foot of the list, there while anything is in it: containers of no project — a docker run, or compose from elsewhere — and processes listening on a port they chose from no project’s directory, an ollama serve, a brew postgres. The desktop’s own listeners stay out, and docker’s proxy, which the containers already say. x, enter and the pane work as under a project; the place is nowhere on disk, so no shell opens in it and no project is made there.

6-5.What x stopped, r brings back where it was. The services the place's compose file declares are what it needs: r starts the ones that are down with docker compose up -d for them, which starts a stopped container and makes again one that was removed, and a compose up running in a shell there takes the service's logs up again, so the shape holds. SECTION 7

Tasks

7-1.t, b and l run the place's tests, build and lint as the project itself defines them. What the project wrote down comes first: a Makefile target, a justfile recipe, a Taskfile task or a package.json script named test, build or lint. Otherwise the ecosystem's own command, by the file that marks the project. Only a linter the ecosystem ships with is guessed at; a project on ruff or eslint names it in a script. A project the guess is wrong for says so in its Makefile, which conn checks first.

Table 7-1.  How a task's command is found

THE PROJECT HASTHE TASK RUNS
Makefile, justfile, Taskfilethe target, recipe or task named for the task
package.jsonthe script named for the task, run with npm
go.modgo test ./..., go build ./..., go vet ./...
Cargo.tomlcargo test, cargo build, cargo clippy
pyproject.tomlpytest; python3 manage.py test for a Django project
Gemfilerspec with a spec directory, else rake test
mix.exs and the restthe ecosystem's own: mix, gradle, mvn, deno, swift, dune

7-2.Each run is a shell named for its task, so its row shows ✓ or ✗, tab goes to a failure, and the place's pane says how each task's last run went and how long ago. The key again replaces a finished run rather than stacking another beside it; a run still going is left to finish. conn test, conn build, conn lint and ctrl-space t, b, l do the same from any shell.

7-3.conn reads the end of the transcript by the shape of the tool's summary line: go test, pytest, jest, vitest, mocha, cargo, rspec, ExUnit, golangci-lint, tsc, ruff, eslint. A failed run's row says test · 3 failed, a passed one 12 passed. A shape it does not know leaves the status alone.

SECTION 8

Stopping

Table 8-1.  Kill keys

xkill the selected process
Xkill it, everything under it, and what shares its process group
x on an entryend the entry's command and its shell; r starts it again
x on a containerstop the container, docker's way
x on a placekill everything running in it
x on a signalled rowkill outright: SIGKILL to what has not gone
Rend the server and every shell it holds

8-1.Every kill asks first: x, y or enter confirms, anything else cancels. Processes get SIGTERM. The question offers the other signals: 9 confirms with SIGKILL, i with SIGINT, for a server that only tears down on ctrl-c, and h with SIGHUP, for a daemon that reloads on it. A signalled row shows a red marker until a scan observes the exit; the list never claims an exit it has not seen. A process that has not gone in five seconds is given up on, and the status line says so; x on it then, or on a row still on its way out, asks to kill it outright, with SIGKILL, which nothing refuses. Kills work on any listed process, including ones conn did not start.

8-2.A held shell is closed through the server. One still running its command is closed only once the command has gone: the command gets SIGTERM, and the shell is hung up when a scan finds it back at its prompt, so a docker compose up stops its containers on the way out; hung up first, it would leave them running. An entry's row is the entry, and the question names it: kill app? The entry is then gone, as an entry nothing runs in is, and r starts it again. An exit that x asked for shows no mark. A tree kill, or an entry's, covers the process group as well as the tree: a parent that exits leaves its children to init and the tree loses them, but the job keeps them. Such a process is listed under its job's leader while the leader runs, and the pane says orphaned of it.

8-3.A container is stopped by docker, which signals the process inside it and follows with SIGKILL after its grace. r brings the service back (6-5).

SECTION 10

The server

10-1.The shells live in a tmux server of conn's own: one per user, for all projects, on a socket at ~/.local/state/conn/tmux-<uid>.sock. CONN_SOCKET moves the socket; XDG_STATE_HOME moves the directory. Every conn writes the server's configuration, the prefix and its chords, the status line, the transcript cap, to ~/.local/state/conn/tmux.conf, brings the server up under it or sources it into one already running, and attaches. No .tmux.conf reaches it.

10-2.The session's first window is the home window: the navigator in the pane down its left, at navWidth through every resize, and the focused shell beside it. Close the navigator and ctrl-space - makes it again. A conn from a newer build restarts the navigator in its pane and re-reads the configuration; the server keeps the shells. Run from a shell inside the window, it does only that. Inside any other tmux it stops with a message, since attaching would nest one tmux in another.

10-3.The server lives exactly as long as it holds something: the home window brings it up, the last window closing takes it down. R, or ctrl-space R from any shell, ends it and every shell it holds, after asking; it is the way to a fresh server. conn restart, typed outside the window, is R and then conn as one command; inside the window it stops with a message, since the pane running it would go with the server. tmux -S ~/.local/state/conn/tmux-<uid>.sock attach is what conn does.

10-5.conn keeps itself current. The navigator asks github which release is latest, on its first paint and once a day after, a plain request for the release page's redirect, kept in ~/.local/state/conn/latest-release. A release newer than the build is said on the status line whenever nothing else is: conn 0.5.0 is out · U installs it. U runs the installer in a popup, aimed at the directory this build runs from, and then conn, which gives the server the new configuration and brings the navigator back as the new build; the shells stay. With nothing newer known, U asks now and says what it finds. A build that is no release, a tree past a tag or a plain go build, is never behind one. Upgrading by hand is the same: install the binary, and the next conn does the rest.

10-6.conn ls is the server's state for scripts: the held shells, one per line, pid, directory, name and exit, tab-separated. The name is empty for a shell opened by hand; the exit is how the shell's command ended, empty while it runs. No server listening is an empty list, not an error.
